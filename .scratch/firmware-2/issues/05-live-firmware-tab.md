# 05 — The Firmware tab updates live

**What to build:**
The Firmware tab on Settings shows a rollout as it happens, without a page refresh: a board checking in, downloading, restarting on the new version, its clean Readings counting up to 10, a hold, Release to all becoming available. Asked for by the owner on the bench, 2026-10-08, watching ESP_64533B update while refreshing by hand.

The dashboard already has a live stream (`GET /api/dashboard/stream`, `sse.ts`). Firmware status is Admin-only (it names WiFi networks), and the stream is not, so the stream carries only a signal that firmware status changed, never the status itself; the open tab then re-reads `GET /api/firmware/status` with the Admin token.

**Blocked by:** none

**Status:** done

**GitHub:** #34

- [x] The stream gains a `firmware` event with no Device data in it (at most the release version), sent when firmware status can have changed: a release published, widened, withdrawn, or held; a firmware check answered (304 or image sent); a Reading whose self-report changes a Device's version or update result; a clean-Readings count moving for a Device in a staged release
- [x] Coalesced on the server, at most one `firmware` event per second, so a fleet's Readings never flood the stream
- [x] The Firmware tab, while open and the page visible, re-reads status on each `firmware` event (one request in flight at a time; one more queued if events arrive meanwhile), and also every 30 s as a fallback, with no flicker and no lost form input
- [x] A small "Live" indicator on the tab, per DESIGN.md: live while the stream is connected; when it drops, "Reconnecting…" and the 30 s fallback continues; the time of the last update stays visible
- [x] Waiting lines' times ("next check by 23:55") and "N of 10 clean Readings" stay current without user action
- [x] Tests: the events at the HTTP seam (each trigger above sends one; a burst sends one; the event carries no hostname, SSID, or token); the tab's refetch logic (event → one refetch, burst → at most two, hidden page → none, fallback timer)

## Comments

**2026-10-08 — built by an agent; awaiting review.** ADR 0007 (new "Update 2026-10-08: the Firmware tab updates live"); README's stream row.

**What was built.** The stream (`sse.ts`) gains a fourth message, `{type: "firmware"}`, with nothing else in it. `Broadcaster.firmwareChanged()` coalesces: the first change starts a window of `firmwareEveryMs` (1 s by default), and one event goes out at its end, saying every change made in it. So a burst is one event, and a steady flow is one a second. With no one connected it does nothing and holds no timer, and `close()` clears a pending one. Callers: the firmware routes (publish 201, widen 200, withdraw 204, and every board check the server records, whether answered 304 or with the image; not an unregistered board's 404, nor a refused publish or widen); ingest, once the report has committed, when the hold check held the release or `rollout.ts`'s new pure `reportMovesRollout(before, after, offered)` says the report changed the Device's version or update result, or (for a Device the release is offered to) its clean-Readings count up to the 10 the tab counts to; the Offline sweep, when its hold check holds. Ingest now reads `update_result` in its locked SELECT to compare. Frontend: `FirmwareEvent` and a `StreamEvent` union in `types.ts`. The hook's message dispatch moved to `lib/streamMessage.ts` (`routeStreamMessage`), which gains `onFirmware`, so every page that passes no `onFirmware` (Dashboard, Campuses, Incidents, History) drops the event, and a non-object message no longer throws. `lib/reload.ts` gains `liveReloads(reload, visible)`, the tab's re-read logic: re-read on `changed()`, and on a 30 s interval, only while visible; a read missed while hidden is made once when the page is shown again. The Firmware tab (`FirmwareSection.tsx`, `useLiveReloads`) subscribes with `onFirmware` and `onReconnect` going to it, through useResource's coalesced reload (one in flight, one queued). It shows `LiveStatus` (the dashboard pages' indicator: green "Live", amber pulsing "Reconnecting") with "Updated 12:35:54 AM" beside it. Waiting times and "N of 10" stay current through the events and the 30 s re-read, each of which re-renders the progress lines against the current time.

**Decisions beyond the ticket.** The event carries no version either: `{type: "firmware"}` only, the least it could say. Trailing-edge coalescing (an event 1 s after the first change) rather than leading-edge, so a burst is exactly one event and is sent after all of it has committed; a lone change shows on the tab about 1 s later. "A Device in a staged release" is read as any Device the current release is offered to (its named Devices, or every Device once widened or published to all), since the progress table shows "N of 10" for each of them; counts past 10 send nothing, since the tab shows nothing more. Device information that changes with every Reading (signal, uptime, free memory) sends no event and waits for the 30 s re-read; so do Devices added, edited or deleted, and `deploy.sh publish-firmware`/`withdraw-firmware`, which run in a process of their own with no stream to tell. The indicator is the existing `LiveStatus`, so it reads "Reconnecting" as on the other pages, not "Reconnecting…". A re-read that fails (the server restarting) keeps the last status on screen with "Could not update the firmware status. ..." under the indicator and the last update time beside it; only a first load that fails shows the error alone (found by eye: useResource's error state blanked the tab at the first 30 s re-read during an outage). The stream stays open while the page is hidden; only the re-reads stop. `firmwareEveryMs` is a Broadcaster option, as `heartbeatMs` is, so the trigger tests use 200 ms; the coalescing tests use the default.

**Tested.** `backend/test/firmwareStream.test.ts` (11), at the HTTP seam over a real SSE subscription: publish, widen, and withdraw each send exactly `{"type":"firmware"}` (no hostname, SSID, Device or Admin token), a refused publish sends none; a board check sends one for a 304 and one for the image, none for an unregistered board; a Reading sends one when its version or update result changes (the Reading message still goes first) and none for the same again, for older firmware, or for a fault report that changes nothing; on a staged release each clean Reading of the named Device sends one up to the tenth, the same from a Device it is not offered to sends none, and the eleventh sends none; a hold sends one from ingest (Sensor fault after taking it) and from the Offline sweep (Offline after taking it), and a second pass holding nothing sends none; a change made while no one listened is not sent later; the default is 1 s; 20 checks at once send one event; a steady flow of checks for 3 s sends 2 to 4 events at least 900 ms apart. Plus `reportMovesRollout` unit cases. `stream.test.ts`'s fallback-network test skips the `firmware` event that a version-carrying Reading now causes. Frontend: `streamMessage.test.ts` (4: a firmware message reaches only `onFirmware`; pages without it ignore it without an error; the other three types as before; unknown types and non-object JSON dropped) and `reload.test.ts` (5 more: an event is one request; a burst while one is in flight is at most one more; a hidden page reads nothing on events or the timer, and once when shown again; hidden and shown without a missed read reads nothing; 30 s fallback with no events, stopped when the tab closes).

**By eye.** The connected Chrome is on another machine and could not reach this one's localhost, so the check ran in headless Chrome here over the DevTools protocol. Setup: the backend against `temperature_alarms_test_rollout`, Vite at 127.0.0.1, and a script playing a bench board. Seen: "● Live · Updated 12:34:54 AM" in green; a release published from another client appeared within 2 s without a reload, while text typed in "Only these Devices" kept its value through every re-read; the board's nudged check, download, restart on 7, and "1 of 10" up to "10 of 10 clean Readings", each about a second after its Reading; "Release to all" became enabled by itself; re-reads stopped after the tenth, apart from the 30 s fallback. Backend stopped: amber "Reconnecting" with the last update time kept, then (after the fix above) the last status kept on screen under "Could not update the firmware status. Could not reach the server". Backend back: "Live" again, re-read on reconnect.
