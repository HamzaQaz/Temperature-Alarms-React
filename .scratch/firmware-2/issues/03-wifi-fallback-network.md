# 03 — A second WiFi network to fall back to

**What to build:**
A board that cannot join its network tries a second configured one before going silent. Useful while closets move between networks (the test board was just moved to the open `CISD-MAC`), and for a closet whose primary SSID is down.

**Blocked by:** none

**Status:** done

**GitHub:** #18

- [x] `config.h`: optional `WIFI_SSID_2` / `WIFI_PASSWORD_2` (empty password: open network, as for the first)
- [x] `network.cpp`: try the first for N seconds, then the second, alternating; stay on whichever joined until it drops
- [x] The self-report names which network the board is on; Settings shows it
- [x] An OTA image carries both, so a board can be moved to a new network over the air by publishing an image whose second network is the new one, then a later image that makes it first
- [ ] Bench run: first network off, board joins the second and reports; first back, board stays until the second drops (`ready-for-human`)

**What was built.** Firmware 7 (`FIRMWARE_VERSION` raised from 6). `config.example.h` gains `WIFI_SSID_2` and `WIFI_PASSWORD_2`, both `""` (no second network); an empty password is an open network, as for the first, and a `config.h` from before firmware 7 (neither defined) builds as with `""`. `network.cpp` holds the two in a table: at boot it joins the first (the 20 s boot wait as before); a network that has not joined within 30 s (`TRY_NETWORK_MS`, the interval the loop already re-issued connects at) hands over to the other, the two in turn until one joins, and the board stays on whichever joined. After a drop the core's own auto reconnect has those 30 s on the same network before the board turns to the other. With one network the loop re-issues the connect every 30 s exactly as before. Serial names the network on every wifi line: `wifi: connecting to closet-net`, `wifi: not joined, trying CISD-MAC (fallback network)`, `wifi: reconnected to CISD-MAC (fallback network), IP ..., hostname ...` (`bench.py`'s `^wifi: (re)?connected` still matches). The self-report, on Readings and fault reports, ends with `"ssid":"CISD-MAC","network":2` (1 for the first). Backend: migration `0020-device-network` adds `devices.wifi_ssid` (VARCHAR(32)) and `devices.wifi_network` (TINYINT UNSIGNED), NULL until a board says; guarded. `deviceInfo.ts` reads `ssid` (cut to 32 printable ASCII characters, WiFi's own limit) and `network` (kept only when exactly 1 or 2); either alone makes a body a self-report, and ingest writes both with the other self-report fields. `GET /api/firmware/status` answers `info.ssid` and `info.fallback` (null before firmware 7); `GET /api/dashboard` answers `onFallbackNetwork` for each Device, and the stream's `reading` and `fault` messages carry it, so a card notes the move with the report that shows it, without a reload. Frontend: the Dashboard card shows "On its fallback WiFi network" in grey with a 16px Wifi icon, under the badges and acknowledgement lines; Settings, Firmware gains a "WiFi network" column: the SSID, with "Fallback network" beneath it in small grey text when it is the second. The OTA box needs no code of its own: `config.h` is compiled into the image, so a published build carries both networks. The README gives the move as three steps: publish a build whose second network is the new one; take the old network away and watch the Firmware tab name the new one; publish a build that makes the new one first, keeping the old one second until it is gone.

**Decisions beyond the ticket.** N is 30 s, the old reconnect interval, so a board with one network behaves as before and a board whose first network is gone reports over its second about 30 s after boot, inside `bench.py`'s 70 s window. After a drop the board does not move at once: the core's auto reconnect keeps its 30 s on the network that dropped, so a router reboot does not move a board; that is how "stay on whichever joined until it drops" reads here. Once on the second network the board does not go back to the first while the second holds (the ticket says stay), and it does not scan for visible SSIDs: the alternation alone. The card says only that the board is on its fallback network, not which: the Dashboard and its stream are public (ADR 0003), and an SSID, especially an open one that admits boards by MAC allowlist, is reconnaissance; the name is on the Firmware tab, behind the Admin token. The board reports which of its two networks it is on and the server derives "fallback" from that, since the server never sees a board's `config.h`. As with every self-report field, the server keeps what the board last said: a report from firmware 6, which names no network, clears it and with it the note; a report that says nothing about itself (firmware 1 and 2) leaves it, and the stream message carries what the server holds. A note, not a Condition (the owner's decision): nothing in Conditions, incidents, the outbox, reminders, the staged rollout's hold, System health, or the worst-first order reads the network. Settings shows it on the Firmware tab, where everything else a board says about itself already is, as one column; History and System health are unchanged. A second network is held to the same rules as the first in "Secrets on the board" (an isolated VLAN, its password in every board). A `WIFI_SSID_2` equal to `WIFI_SSID` is not guarded against: harmless, though a board that joins on its second turn shows the note. `FIRMWARE_VERSION` 7, as the task set it (the sensor ticket took 6).

**Tested.** `deviceInfo.test.ts` (5 more, at the HTTP seam on the test MySQL): a board on `closet-net` as network 1 shows its `ssid` with `fallback: false` and no note, then on `CISD-MAC` as network 2 shows `fallback: true` and `onFallbackNetwork` on its card, the other Device's card none, and the network's name appears nowhere in the Dashboard's answer; a fault report names the network too (202, then shown); a later report from firmware 6 clears it and the note; `network` 0, 3, `"2"`, 1.5 and null are dropped with a 201, an SSID with CR LF and 60 characters is cut to 32 printable ones, a non-string SSID is dropped, and `network` alone is still a self-report; and with email on, four Readings from a board on its fallback network leave no Condition, no open incident, and nothing in `incidents` or `notifications`, while one Hot Reading on the same server then opens one and queues one. `stream.test.ts` (1 more): the `reading` and `fault` messages carry `onFallbackNetwork` and never the SSID, a report with no self-report keeps the server's value, and a report from network 1 clears it; its shape test and `dashboard.test.ts`'s two shape tests expect `onFallbackNetwork: false`; the migration tests list `0020-device-network` and re-run it when it landed unrecorded.
