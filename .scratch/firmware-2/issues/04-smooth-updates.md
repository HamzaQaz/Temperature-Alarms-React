# 04 — Firmware updates that say what is happening

**What to build:**
Publishing a build should either reach the boards it names or say plainly why not, and the Firmware tab (and `deploy.sh firmware-status`) should show each board's way to the new version step by step. Found on the bench, 2026-10-07: firmware 7 was uploaded on Settings, the test board (ESP_64533B, on firmware 4) checked 30 s after a reset and was told "none newer", and nothing anywhere said the release did not include it. Its serial log prints the network hostname `ESP-64533B` (hyphen) while the Device is `ESP_64533B` (underscore), an easy name to get wrong in "Only these Devices".

**Blocked by:** none

**Status:** done

**GitHub:** #30

- [x] Publishing with `only` checks each name: `ESP-64533B`, `esp_64533b`, and `64533B` are read as `ESP_64533B`; a name that matches no registered Device is refused (422) naming it, before anything is stored, in the API, the Firmware tab, and `deploy.sh publish-firmware --only`
- [x] The publish answer, and the Firmware tab after it, say who it is offered to: "Offered to ESP_64533B (CHS IDF 2, running 4)", or "Offered to every Device (12)"; publishing that would reach no Device is refused
- [x] Per offered Device, one line with where it is: waiting for its next check → downloading (the server sent the image) → running the new version → N of 10 clean Readings; or stuck: never checked in, refused the image (its update result), Offline
- [x] Each waiting line says when to expect the next step: a board that sends Readings checks at its next one, nudged by `X-Firmware-Available` (firmware 4 already does: on the bench it logged `update: version 7 is waiting, checking now` within one Report interval); one that is silent checks hourly and 30 s after a restart, so "next check by 23:55, or restart the board"
- [x] The board's serial log says what the server answered (on the bench the ~60 s download and signature check printed nothing between `checking now` and the restart): `update: v7 offered, downloading`, `update: installed, restarting`, `update: refused, <reason>`, and for a 304 `update: none newer for ESP_64533B (running 4)`, so a bench log names the Device the server knows it as
- [x] `deploy.sh firmware-status` (and `deploy.ps1`) prints the same per-Device lines
- [x] Tests: name forms accepted and an unknown name refused; the per-Device states at the HTTP seam (never checked, sent, running, counting, failed); the expected-next-check text for old and new firmware

## Comments

**2026-10-07 — bench result.** After republishing with `only=ESP_64533B`, the board went from 4 to 7 over the air in about 70 s: the nudge with its next Reading, a silent ~60 s download and check, then a restart on 7. So the delay was entirely the release not naming it.

**2026-10-07 — built by an agent; awaiting review.** ADR 0007 (new "Update 2026-10-07: publishing says who it reaches, and where each board is"); README ("Updating boards over the air", the firmware API rows) and DEPLOYMENT.md updated.

**What was built.** `firmwareStore.ts`: `readHostname` reads `ESP-64533B`, `esp_64533b`, `ESP64533B` and `64533B` as `ESP_64533B`; `publishFirmware` now checks its audience before anything is stored: a name that is not a hostname, or that no Device is registered under, is refused (`FirmwareImageError`, so 422 in the API and `Refused: ...` from `deploy.sh publish-firmware --only`), naming it as typed with the hostname it was read as (`no Device is registered as 64533c (ESP_64533C); check the hostname on its card, or add it in Settings first`), and so is a release for every Device while no Device is registered. `offeredTo` says who a release reaches: `Offered to ESP_64533B (CHS IDF 2, running 4)` (`version not known yet` before a board has said), `Offered to every Device (12)`, or `Offered to no Device while it is held`; POST /api/firmware and /widen answer with it as `offeredTo`, and the status's release carries it. `rollout.ts` gains the pure `progressOf`: per offered Device one step, Offline first (it stops everything), then `running` (the new version or later), `refused` (`failedToInstall` against the update result its last Reading carried), `downloading` (the server sent it this release's image), `never-checked`, `held`, else `waiting`; `unregistered` for a named Device deleted since. A Device still to take it gets `nextCheck`: `reading` (at its next Reading, by its last report plus a Report interval) for a board that reports and says its version (firmware 3 and later, which takes the `X-Firmware-Available` nudge), else `hourly` (its last check plus an hour: a silent board, or firmware before 3). `STEP_TEXT`, `nextCheckText` and `progressDetail` put it in words ("Waiting for its next check: by 23:55, or restart the board", "due by 23:35; restart the board" once past, "at its next Reading, by 23:40", "the server sent the image at 23:39", "4 of 10 clean Readings", the update result for a refusal, "last report at 22:10, next check by ...", "flashed before over-the-air updates or built without public.key; it needs a USB flash"). `releaseProgress` reads the offered Devices (a staged release's named ones, else every Device) and orders them stuck first, then waiting, downloading, running, each by Campus, Closet, hostname; GET /api/firmware/status adds `progress: {cleanReportsToWiden, devices}`. `firmwareCli.ts` (so `deploy.sh`/`deploy.ps1 firmware-status`): the release line, the `Offered to ...` sentence, one aligned line per offered Device (`  ESP_64533B  CHS IDF 2  version 4  Waiting for its next check: by Oct 7, 23:55 CDT, or restart the board`, times on the server's clock), then every Device's version as before; publish prints the release and who it reaches. Firmware tab: the summary says `Version 8 is published, since ... Offered to ...`; the "Still on an older build" list is gone, replaced by a table with one row per offered Device (Device with its Campus and Closet, Version, Where it is: the step in medium weight, the detail beneath in Dimmed Grey), under "Named Devices first" (its note, the hold and Release to all, as before) or "Where each Device is"; Offline shows as the Offline badge in its warning look, a refused image or a deleted Device as an error (Critical Red text, AlertCircle), a Sensor fault the server reports as its Condition badge; the status line after Publish and Release to all leads with the server's `offeredTo`. Firmware 8 (`updater.cpp`): `ESPhttpUpdate.onStart` logs `update: v8 offered, downloading` (the version from the latest `X-Firmware-Available`; `a newer build offered` if none was heard), `onEnd` logs `update: installed, restarting` (flushed before the restart), a failure after the image started arriving (or for want of room) logs `update: refused, <reason>`, one before it `update: failed, <reason>` (adding `is ESP_64533B registered?` on a 404), and a 304 `update: none newer for ESP_64533B (running 8)`; the result it reports stays `failed, ...`, which the hold reads. `reporter.cpp` now tells the updater on every accepted report whether a build waits (0 when none), so a withdrawn release is not named. `FIRMWARE_VERSION` is 8. `deploy.sh`/`deploy.ps1`: help for `firmware-status` and `--only`, and the next step after `--only` points at `firmware-status` and the 10 clean Readings.

**Decisions beyond the ticket.** From the coordinator's correction (the ticket wording of 996b477, taken into this file): a board that sends Readings checks at its next one; the rule used is "reports and says its version" (firmware 3 and later, the nudge's own version), not firmware 5. "Would reach no Device" is read as no registered Device to offer it to (every Device while none is registered); a named Device already on the version is still offered it (it counts for the stage and the hold). Offline outranks every other step, since nothing moves while a board is silent; a waiting or Offline board's next check is shown only while it has not taken the release. The `unregistered` and `held` steps are additions, for a named Device deleted after publishing and for boards not offered a held release. The CLI gives times as `Oct 7, 23:55 CDT` on the server's `TZ`; the tab gives the browser's time (with the date when not today). The tab's per-Device table replaces the staged table's Last report, Health and Clean Readings columns (the clean count is in the line, Offline and Sensor fault are badges in it). The firmware's serial line for a nudge (`update: version 8 is waiting, checking now`) is unchanged. No migration was needed.
