# 01 — Staged rollout with an automatic hold

**What to build:**
Publishing to named Devices first already exists (`POST /api/firmware?only=ESP_A,ESP_B`, ADR 0007). Add the second half: the Firmware tab shows how the first boards are doing on the new version, offers "Release to all" once they have reported on it, and holds the release by itself if one of them goes Offline, raises Sensor fault, or reports a failed update after taking it.

**Blocked by:** none

**Status:** done

**GitHub:** #16

- [x] The release records its stage (named Devices, or all) and when it was widened
- [x] `POST /api/firmware/widen` (Admin token) turns a staged release into one for every Device
- [x] Hold: a staged Device that took the new version and then goes Offline or Sensor fault, or whose self-report carries a failed update, marks the release held; held releases offer nothing more, and the Firmware tab says why and which Device
- [x] Firmware tab: per staged Device, its version, last report, and health; "Release to all" enabled only when every staged Device reported on the new version for N intervals
- [x] Tests at the HTTP seam: widen, hold on Offline, hold on a failed update, no hold for a Device that never took it

**What was built.** Migration `0015-staged-rollout` adds `firmware_release.widened_at` and the hold (`held_at`, `held_hostname`, `held_reason`, `held_detail`), `devices.firmware_sent_at` (DATETIME(3)) and `devices.firmware_clean_reports`, makes `notifications.incident_id` nullable, and adds `hold` to `notifications.kind` beside whatever kinds the column already has (read from `information_schema`, so a sibling's kind is kept); all guarded so a run that died before being recorded repeats. The release (`firmwareStore.ts`) now carries `staged` (the named Devices it went to first; `only_hostnames` keeps them after widening), `stage` (`named` or `all`), `widenedAt`, and `hold`; `only` still means who it is offered to now. `POST /api/firmware/widen` (Admin token) sets `widened_at` (200 with the release; no change if it already goes to every Device; 404 with nothing published; 409 naming the Device and why while held); publishing the same build again without `only` does the same (and keeps `published_at`), with `only` it re-stages it, and a held build is refused (422). `rollout.ts` holds the pure rules: `cleanReportsAfter` (a Reading on the version of the report before, within two Report intervals of it, adds one; another version or a missed interval starts at one; a fault report, or no version, is 0), `readyFor` (on the version or later with 10, `CLEAN_REPORTS_TO_WIDEN`), and `failedToInstall` (`failed, ...`, after the server sent this release, still behind). Ingest keeps the count on the Device under its row lock; the update check zeroes it when the board's version changes and stamps `firmware_sent_at` (to the millisecond) when it sends the image. The hold: the Offline sweep, after each pass, holds the staged release if a named Device that took it (sent the image since publication, or reporting the version) has an Offline or Sensor fault incident that started after it took it (`holdOnIncidents`); ingest, after a named Device's report commits, holds it for a failed update, or for a Sensor fault opening (`holdOnReport`, against the cached release, so other Devices pay nothing; a failure is logged and never costs the Reading). `holdRelease` is one guarded UPDATE (same version, staged, unheld, Device named) and, with notifications on, a `hold` row in the same transaction. Held, `offers` is false: no image, no `X-Firmware-Available`. The sender (`notifier.ts`) sends due `hold` rows as their own email ahead of any Incident digest, built by `holdEmail.ts` from the hold as it stands (`[Temperature Alarms] Firmware 7 held: ESP_A1B2C3 went Offline`, the Device's Campus and Closet, when, what to do, a link to `/settings?tab=firmware`), and drops them unsent once no release is held (`dropStaleHolds`). `GET /api/firmware/status` adds `rollout` for a staged release: per named Device its version, last report, Conditions (Offline and Sensor fault from its reports, server-judged), clean Readings and `ready`, plus `cleanReportsToWiden` and `ready` (every one ready and not held). The Firmware tab shows that as "Named Devices first": a table (Device, Version, Last report, Health as the Online/Offline and Condition badges, Clean Readings "4 of 10"), "Release to all" (outline, enabled only when `ready`) with a note naming who is not there yet, or, held, the hold in Critical Red text ("Held on ...: ESP_A1B2C3 went Offline after taking it.") and no button; the release sentence says when it was widened and who had it first, or that it is held. `firmwareCli.ts status` (`deploy.sh firmware-status`) says `held since ... (ESP_A1B2C3 went Offline after taking it), offered to no one`, or when it was widened. README ("The hold", steps 3 and 4), DEPLOYMENT.md, ADR 0007 and CONTEXT.md updated.

**Decisions beyond the ticket.** "Took the new version" counts from the download, not only from the board reporting the new version: a board that cannot join WiFi with the new build never reports again, which is the case the stage exists for; a board on the version already (flashed over USB) counts too. The incident must start after it took the build, so an Offline stretch before the download holds nothing. A failed update counts only from a report that arrived after the server sent the Device this release (to the millisecond, since the board posts its Reading, gets the nudge, and checks within the same second) and while the Device is still behind: the board keeps its last result until it checks again, so a failure from an earlier release must not hold this one. Holds apply only while staged: a widened release is never held (one closet losing power must not stop the fleet). A hold is lifted only by withdrawing the build or publishing a higher version; widening and re-publishing the same build are refused. The server does not refuse an early `widen`: the tab enables it only when ready, and the Admin (or `deploy.sh publish-firmware` without `--only`) may know better. Clean means a good Reading in each Report interval: a fault report or a missed interval (more than two intervals since the last report) restarts the count. A Bench Device's hold is emailed (it is about the release, not the closet). The hold email is its own email, never in an Incident digest, read at send time and dropped if the release was withdrawn or replaced; the outbox row takes the held Device as its device, no Incident, level `warning`. Health on the tab is the server's Offline and Sensor fault Conditions for the Device, not a word the browser picks. Staged hostnames with no registered Device show as "Not registered" and keep "Release to all" off. No `widen-firmware` command was added to the deploy scripts: publishing the same file without `--only` already widens.

**Tested.** `stagedRollout.test.ts` at the HTTP seam through the real app, sweep and sender with a test relay: widen (401 without the Admin token, 200 with `stage: all`, `only: null`, the named Devices kept, `widenedAt` set, `publishedAt` kept, the other board then offered the image, again no change, 404 once withdrawn); "Release to all" only after 10 clean Readings on the new version from every named Device (9 not ready, 10 ready, a board already on the version counts, a fault report zeroes the count without holding); hold on Offline (the board that downloaded it goes silent, the one that did not holds nothing; status, 304 and no nudge for the other named board, widen 409 and re-publish 422 naming why, the hold emailed alone before the Incidents' digest with its subject, Device line and Settings link, a higher version starts unheld); hold on a failed update (reported after the download, not offered even to that board, nothing queued with email off); hold on Sensor fault on the third fault report (two hold nothing), the `hold` row has no Incident, and is dropped unsent when the build is withdrawn; no hold for a Device that never took it (a failure reported before the download, then Offline); no hold once widened; the same build published again for all widens. The pure rules (`cleanReportsAfter`, `readyFor`, `failedToInstall`). `firmware.test.ts`: `firmware-status` says held and why, and `publish-firmware` refuses the held build.
