# 03 — Recipients per Campus

**What to build:**
Each Campus can name its own recipients, so a campus's technicians get only their campus's mail. `NOTIFY_TO` stays the default for any Campus without its own list, and can be told to receive everything.

**Blocked by:** none

**Status:** done

**GitHub:** #13

- [x] Migration: `campuses.notify_to` (comma-separated addresses, empty: use `NOTIFY_TO`)
- [x] Campus editor on Settings gains the field, checked with the same address rule as `config.ts`
- [x] The sender groups due rows by recipient list: one email per list per pass, each still coalesced and worst first; a row is marked sent only when its own email went
- [x] `NOTIFY_TO_ALL=true` (or similar) keeps the global list on every email, for a district office that wants all of it
- [x] Settings status shows the last result per list
- [x] Tests: two Campuses, two lists, one outage each, two emails; a failing list retries without resending the other

**What was built.** Migration `0014-campus-recipients` adds `campuses.notify_to` (VARCHAR(1000), empty by default: the Campus emails `NOTIFY_TO`) and `notifications.recipients` (TEXT, NULL until a row's first try: the list it was last tried with), both guarded so a run that died before being recorded repeats cleanly. `config.ts` exports `parseAddressList`, the comma-separated bare-address rule `NOTIFY_TO` already used, and reads `NOTIFY_TO_ALL` (`true` or `false` in any case, empty is false, anything else refused at startup) as `notifications.toAll`; Compose passes it as `${NOTIFY_TO_ALL:-}` and both `.env.example` files list it. `campusInput.ts` gains `parseRecipients` (a string or an array of strings, every entry checked by `parseAddressList`, 1000 characters at most once stored as `a@x, b@y`). The Campus API: `POST /api/campuses` takes an optional `notifyTo`; `GET /api/campuses/recipients` (Admin token) gives each Campus's own list by name, `[]` for one on `NOTIFY_TO`; `PATCH /api/campuses/:id` with `{notifyTo}` (Admin token) replaces it, refusing a body without the field (422), and answers `{id, name, shortcode, notifyTo}`. The public `GET /api/campuses` still carries no address. `outbox.ts` gains the pure `recipientsFor` (the Campus's own list, or `NOTIFY_TO` for a Campus without one and for a row with no Campus; with `NOTIFY_TO_ALL`, `NOTIFY_TO` after the Campus's own; each address once whatever its case, in the order named), `listKey` (the addresses lower-cased and sorted, so the same people in any order or case are one list), `byRecipients` (due rows grouped by key, in the order each list first appears), and `recipientLists` (every list email can go to now, `NOTIFY_TO`'s first, with the shortcodes of the Campuses on it, the Bench on none). The sender (`notifier.ts`) now gives each list its own turn: `sendNextList` claims what is due as before (`FOR UPDATE SKIP LOCKED` at read committed), drops stale reminders, reads each row's list from its Device's Campus with a plain `LEFT JOIN` read (no lock on a Device or Campus), and sends the first list whose own window has passed (`readyToSend` per list) and which has not had its turn this pass, as one email to that list (`Email.to`, which the mailer now honours; the test email still goes to `NOTIFY_TO`), then marks those rows sent, or records the failure and backoff on those rows only, and commits. `runNotifierPass` repeats that until no list is ready, then rejects with the first `MailerError` if any list failed, so the other lists still went. Mark and failure both store the list's key in `notifications.recipients`; `outboxStatus` reads the last try per key from the rows. `GET /api/notifications/status` adds `toAll` and `lists` (`{recipients, campuses, isDefault, lastResult}`), the test email counting as `NOTIFY_TO`'s latest result. Frontend: `lib/recipients.ts` repeats the address rule and the 1000-character limit for the forms; Settings, Campuses, with the Admin token, shows a Recipients column ("Default recipients" in muted text for a Campus without its own), an optional Recipients field on the Add form, and a pencil per row that turns it into `EditCampusRecipientsForm` (one field, Save recipients and Cancel, focus back on the pencil, the outcome said in the status line: "Central High School emails chs-techs@district.example."); without the token the column is not shown, since the server would not give the addresses. Settings, Notifications, lists each recipient list (addresses, "Default recipients (NOTIFY_TO), for CHS, MHS and the test email." or "For NHS.", and "Last sent …", "Last failure …" in red with its icon, or "Nothing sent in the last week."), replacing the one "Sent to" line and the global last-sent and last-failure lines; the section description says a Campus can name its own. Deploy: `NOTIFY_TO_ALL` is a tunable in `deploy.sh` and `deploy.ps1` (`--set NOTIFY_TO_ALL=true`, `false` or empty; anything else refused before `.env` changes; skipped when left empty in the interactive tunables). README (API table, deploy paragraph), DEPLOYMENT.md (Email notifications), the deploy skill, CONTEXT.md and ADR 0008 updated.

**Decisions beyond the ticket.** Decided by the coordinator, open to the owner: `NOTIFY_TO_ALL` is the name, off by default, ignored while email is off like the window, and copies `NOTIFY_TO` onto every Campus email rather than sending the office a separate digest; it is set with `deploy --set` (a tunable), not its own flag. Mine: the addresses are kept out of the public Campus list and read through an Admin-token route (the Notifications status already treats addresses as Admin-only); the list is edited by `PATCH /api/campuses/:id` with `notifyTo` as its only field (CORS already allows PATCH, not PUT), and a body without it is refused rather than taken as "clear"; only the recipients are editable, not the name or shortcode. A list is identified by its addresses lower-cased and sorted, so two Campuses naming the same people share one email, while the email itself keeps the order and spelling written (the Campus's own first, then `NOTIFY_TO`). The list is read when the email is built, not when the row was queued, so an edit applies to rows already waiting, as the Incident itself is read at send time. Each list is its own transaction with one turn a pass, so a refused list neither holds back nor resends another, a retry in one never hurries another's window, and a pass cut short rolls back only the list in flight; the pass still claims at most 200 due rows, so a list beyond those waits for the next pass. A row with no Campus (none today; the monthly report row a sibling ticket adds) goes to `NOTIFY_TO`. The test email still goes to `NOTIFY_TO` only and counts as that list's last result; there is no per-Campus test button (a Campus's list gets its first real email). The Bench appears on no list on Settings, since it never emails. Settings, Notifications, no longer shows the global last-sent and last-failure lines (the API still returns them): the per-list results cover them.
