# 01 — Graceful shutdown

**What to build:**
On SIGTERM (every `docker compose up -d` that recreates `api`, and every `deploy`), the backend stops taking requests, lets the notifier and Offline sweep finish the pass they are in, closes SSE streams, and closes the pool, all within Docker's 10 s grace. Today `index.ts` starts the retention job, the Offline sweep, and the notifier and never stops them, so a deploy can cut a sender pass mid-send (it rolls back and resends, which ADR 0008 accepts, but a clean stop avoids the duplicate).

**Blocked by:** none

**Status:** done

- [x] `startRetentionJob`, `startOfflineSweep`, and `startNotifier` each return a `stop(): Promise<void>` that clears the timer and waits for an in-flight pass
- [x] `index.ts` handles SIGTERM and SIGINT: `server.close()`, end SSE streams (clients reconnect in 2 s), stop the jobs, `pool.end()`, exit 0; a second signal or 8 s exits at once
- [x] Health answers 503 while stopping, so a proxy stops sending
- [x] Tests: `stop()` waits for a pass in flight; a test server shuts down cleanly with a stream open

## Comments

**2026-10-07 — built by an agent; awaiting review.** ADR 0008 (a stop waits for the sender's pass); README (health while stopping); DEPLOYMENT.md (pm2 gives a stop 10 s).

**What was built.** `startRetentionJob`, `startOfflineSweep`, and `startNotifier` keep the promise of the pass in flight instead of a flag, and their `stop()` clears the timer and resolves once that pass has settled; a tick during a pass is still skipped, and none starts after the stop. The retention job's stop also ends its pass after the batch it is deleting (an `AbortSignal` handed to `deleteReadingsPastWindow`), which logs `retention: stopped after removing N readings; the next pass removes the rest`. New `backend/src/shutdown.ts`: `shutDown({ server, sse, jobs, pool })` calls `server.close()`, ends every SSE stream with `retry: 2000` (new `Broadcaster.close()`, which also answers later stream requests 503 and empties the client set at once, so a Reading or sweep pass still in flight broadcasts to no one rather than writing to an ended response), waits for every job's `stop()` and for the server to close, closing keep-alive connections as they go idle, then `pool.end()`. `exitOnSignals(stop)` runs it on the first SIGTERM or SIGINT and exits 0, or 1 if it failed; a second signal, or 8 s (`STOP_DEADLINE_MS`) without finishing, exits 1 at once. `index.ts` keeps the jobs, sets a `stopping` flag first (passed to `createApp` as `AppDeps.stopping`), and `GET /api/health` answers 503 `{"status":"stopping"}` from then on, without asking the database. Logs: `SIGTERM: stopping; a second signal exits at once`, then `Stopped`, or `still stopping after 8 s: exiting now`. Node is PID 1 in the `api` container, where a signal with no handler is ignored, so until now every stop waited out Docker's 10 s and was then SIGKILLed; a deploy's `api` stop now takes well under a second when nothing is in flight.

**Decisions beyond the ticket.** Retention's stop ends its pass between batches rather than waiting it out: the first pass after a legacy migration can take minutes, and deleting is idempotent, so the next start finishes it. The sweep and the sender finish their passes whole, as the ticket asks; a sender pass held up by a relay past the 8 s still rolls back and resends, as ADR 0008 accepts. Exit code 1 for every forced exit (second signal, deadline, a failed stop). Node's `server.close()` leaves the connection of a request in flight open for its whole 5 s keep-alive after the answer (measured: 6.3 s to close), so while stopping the server closes idle connections every 50 ms; requests in flight are answered, never cut. The 2 s goes out as the SSE `retry` field on the ending frame only, so streams that drop for other reasons keep the browser's default (3 s in Chrome); a stream request after the close gets 503, which `use-reading-stream.ts` already reopens after 5 s. `backend/ecosystem.config.js` gets `kill_timeout: 10000`, since pm2 sends SIGINT and by default SIGKILL 1.6 s later. Health while stopping skips the database check and carries no `database` field. A signal during startup, before the migrations finish and the server listens, is not handled: it is ignored as before until Docker's SIGKILL.

**Tested.** `shutdown.test.ts` (7): a real app with a dashboard stream open, a keep-alive connection sitting idle, and a job whose pass is held: the server stops listening at once, the stream gets `retry: 2000` and ends, the shutdown waits for the pass (the pool still answers meanwhile), then finishes in under a second with the pool closed; a request in flight on a keep-alive connection is answered and the stop still finishes in under a second (it took 3 to 5 s without the idle sweep); `exitOnSignals` with a stand-in process: SIGTERM and SIGINT each run the stop once and exit 0, a second signal exits 1 at once without a second stop, a stop still running at the deadline exits 1, a failed stop exits 1. `retention.test.ts`: stop waits for the DELETE in flight, runs no further batch (one of three batches done, the log line), and the next pass removes the rest. `incidents.test.ts`: the sweep's stop waits for the held pass, which opens its Offline incident, ticks during it are skipped, and no pass runs after. `notifier.test.ts`: stop waits for a send held in the relay, the row is marked sent before it resolves, and a later pass sends nothing again. `stream.test.ts`: close ends both streams with the 2 s retry, empties the set, refuses a new stream with 503, and a Reading broadcast after it is harmless. `health.test.ts`: 503 `{"status":"stopping"}`. The existing scheduling tests now await `stop()`. Each new test was checked against a mutation (no idle sweep; `stop()` not awaiting the pass; retention not aborting): each fails, and a failure releases its held pass, so it fails rather than hangs.

**Untested.** A real `docker compose up -d` recreate or `deploy` (the container's stop time and log lines, and a browser reconnecting through nginx in 2 s); `pm2 restart` with the new `kill_timeout`; real signals to a running `node dist/index.js` (the wiring in `index.ts`, as `main()` is not under test); a real relay slower than 8 s at the moment of a stop.
