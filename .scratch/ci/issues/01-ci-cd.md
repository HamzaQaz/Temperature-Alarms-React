# 01 — CI/CD: test the server and firmware on every push, publish build artifacts

**What to build:**
GitHub Actions for the repo (there is no CI today): every push and pull request runs the checks a developer runs before a commit, and `master` publishes what it builds, without deploying it anywhere.

**Blocked by:** none

**Status:** done

**GitHub:** #23

**CI** on every push and pull request:
- [x] backend: typecheck (test + production) and `npm test` against a MySQL 8.4 service container
- [x] frontend: typecheck, lint, test, build
- [x] firmware: `arduino-cli` with esp8266 core 3.1.2 compiles `arduino/TemperatureAlarms` for `SENSOR_TYPE` DHT11, DHT22 and SHT31 (from `config.example.h`, no secrets), and `arduino/test_bench.py` runs
- [x] deploy scripts: `deploy.test.sh` (with shellcheck) on Linux, `deploy.test.ps1` on Windows (pwsh 7 and PowerShell 5.1)

**CD** (owner decision 2026-10-07: build artifacts only):
- [x] on `master`: build the api and frontend images and publish them to GHCR, tagged with the commit and `latest`
- [x] on `master`: attach the unsigned firmware builds (one per sensor type) to the workflow run; no signing in CI (`private.key` stays local), no auto-deploy

**What was built.** One workflow, `.github/workflows/ci.yml` ("CI"), on every branch push and every pull request, top-level permissions `contents: read`, every checkout without persisted credentials, the default shell named `bash` so a failing command in a pipe fails its step. Jobs, all in parallel: **Backend** (Node 22, npm cache, `npm ci`, `npm run typecheck`, `npx tsc --noEmit -p tsconfig.json`, `npm test` with `TEST_DATABASE_URL` pointing at a `mysql:8.4` service container set up like `backend/docker-compose.yml`: database `temperature_alarms_test`, user `temp`, data in tmpfs, the job starting once `mysqladmin ping` answers). **Frontend** (Node 22, npm cache, `npm ci`, typecheck, lint, test, build). **Firmware**, a matrix over DHT11, DHT22 and SHT31: arduino-cli 1.5.1 from its GitHub release, checked against its SHA-256; `~/.arduino15` and `~/Arduino/libraries` cached under a key made of the CLI version, the core version, and a hash of the library list, and only on a miss `core update-index`, `core install esp8266:esp8266@3.1.2` (the board index URL given through `ARDUINO_BOARD_MANAGER_ADDITIONAL_URLS`, no config file) and `lib install --no-deps` of DHT sensor library 1.4.7, Adafruit Unified Sensor 1.1.15, Adafruit SHT31 Library 2.2.2 and Adafruit BusIO 1.17.4, the download staging dropped before the cache is saved; then `config.h` is `config.example.h` with only the `SENSOR_TYPE` line changed (checked with `grep -x`), `arduino-cli compile --fqbn esp8266:esp8266:nodemcuv2`, and the RAM, IRAM and flash lines go on the run's summary. **Bench watcher** (`python3 -m unittest arduino/test_bench.py` on the runner's Python). **Deploy scripts (Linux)**: shellcheck 0.11.0 from its release, checked against its SHA-256, over `deploy.sh`, `deploy.test.sh`, `real-ip.sh` and `real-ip.test.sh`, then `bash deploy/deploy.test.sh` and `sh frontend/real-ip.test.sh`. **Deploy scripts (Windows)**: `deploy.test.ps1` under `shell: pwsh` and again under `shell: powershell`. **Image** (api from `backend/`, frontend from `frontend/`), which needs every job above: Buildx with the GitHub Actions cache (a scope per image), tags `ghcr.io/hamzaqaz/temperature-alarms-react-<api|frontend>:<full SHA>` and `:latest`, OCI labels `org.opencontainers.image.source` (the repository) and `.revision` (the SHA); it builds on every run and logs in to ghcr.io with `GITHUB_TOKEN` and pushes only for a push to `master` (`PUBLISH`). On `master` each firmware job also uploads its `TemperatureAlarms.ino.bin` as the artifact `firmware-<SENSOR>-unsigned`, failing if the file is missing. Concurrency groups runs by workflow and ref: a newer push cancels a branch's or pull request's run in progress; on `master` a started run finishes and the newest waiting run follows it. Every job has a timeout (backend 30 minutes, firmware and images 20, the rest 5 to 10). No secret beyond `GITHUB_TOKEN`; nothing signs firmware or touches a key; nothing deploys. README: a "CI" section under "Working on the code" lists the jobs, what `master` publishes and where, why the firmware artifacts are not for boards (placeholder `config.h`, unsigned), and that the pinned versions in the workflow change with the README's libraries table.

**Decisions beyond the ticket.** Mine, open to the owner. One workflow with CD as gated jobs rather than a second workflow: the images are pushed only when every check on the same commit passed. The images are built on every run, pushed only from `master`, so a broken Dockerfile shows on its branch; the image job therefore holds `packages: write` on branch runs too, with nothing to push there (a fork's pull request gets a read-only token regardless). Images are linux/amd64 only, named `api` and `frontend` (the Compose service is `web`), with the build's default provenance. Each firmware build is attached by its own compile job on `master`, not held until the other jobs pass, and keeps the default retention. On `master` runs queue instead of cancelling, so `latest` never steps back to an older commit. arduino-cli and shellcheck are downloaded at pinned versions with pinned checksums instead of `arduino/setup-arduino-cli` (still on the deprecated Node 20 runtime) and the runner's preinstalled shellcheck (whose version moves with the image); arduino-cli 1.5.1 is the version this repo's builds were checked with locally, shellcheck 0.11 the one the deploy scripts were last checked with. `--no-deps` installs exactly the four pinned libraries (the README's command lets arduino-cli resolve the two dependencies, which can pick newer ones). `real-ip.test.sh` and shellcheck over `real-ip.sh` ride in the Linux deploy-scripts job: the README lists it with the other checks and it is the same TRUST_PROXY gate. The push trigger is limited to branches, so a tag alone runs nothing; a branch with an open pull request runs twice (push and pull_request), as the ticket asks for both. Node 22 (the newest 22.x), as the images and the README's 22.18 floor. The README section stays out of the repository layout tree, to keep the coordinator's merge with sibling tickets small.
