# 02 — Export History to CSV

**What to build:**
A "Download CSV" on a Device's History page for a date range: one row per Reading (local time, UTC time, °F, °C, % humidity), so someone can chart it in Excel or attach it to a work order. Incidents for the same range as a second download.

**Blocked by:** none

## Comments

**2026-10-07 — built by an agent; awaiting review.** README (API table: the two downloads, History's `retentionDays`).

**What was built.** `routes/csvExports.ts`, mounted at `/api` ahead of the other routers, serves both downloads, public like History and the Incidents log (no token; the read rate limit applies). `GET /api/devices/:id/readings.csv?from=&to=&tz=` takes whole days in `tz` (the server's zone by default), both ends included and cut at local midnight with `localDay`, at most `RETENTION_DAYS`: one row per Reading, oldest first, with the local time and the UTC time as `2026-09-05 14:30:00` (`wallClockText`, new in `localDay.ts`), °F, °C to one decimal, and % humidity (empty when null). `GET /api/incidents.csv?from=&to=&tz=&device=` takes the Incidents log's own `from` and `to` instants (`parseWindow`, now exported with a maximum), up to `RETENTION_DAYS` plus one day, and `device=` for one Device's: Campus, Closet, hostname, Condition, worst level, start and end in local and UTC time (empty while ongoing), duration in minutes, peak °F, °C, humidity and when, and who acknowledged it and when. Both send a header row, CRLF line ends, bare numbers (no `°` in values or headers), UTF-8 with a byte order mark, and `Content-Disposition: attachment` named `CHS_IDF-2_readings_2026-09-01_to_2026-09-28.csv`, `incidents_2026-10-04_to_2026-10-05.csv`, or `CHS_MDF_incidents_…` with `device=` (one date for a single day). Streamed: an async generator reads 5,000 rows at a time by keyset (after the last row's time and id, so each query walks `ix_readings_device_recorded_temp` on from where the last stopped; incidents through the new `incidentsOverlappingPage`), and `stream.pipeline` writes each page to the response, chunked, at the pace the socket drains. A client that goes away stops the reads; a database error partway cuts the connection, so the download fails rather than ending as a short file that looks complete. `csv.ts`: `csvCell` writes text that starts with `=`, `+`, `-`, `@`, a tab, or a carriage return with a leading `'`, quoted (OWASP, CSV injection), and quotes any text with a comma, quote, or line break; `fileNamePart` keeps a Campus shortcode or Closet name to letters, digits, dots and hyphens. History's JSON gains `retentionDays`. Frontend: History's header gains an outline "Download CSV" beside Reset history, opening a dialog: First day and Last day (both the day on screen when it opens; native date fields bounded by the Retention window back from today), a line saying how many days or what is wrong, then "Download incidents" (outline) and "Download Readings" (the dialog's one primary). The Incidents page gains an outline "Download CSV" after the window controls, for the window they name ("Download CSV of the incidents, Wed, Oct 7" to a screen reader). Every download is a plain `<a download>` link (`readingsCsvUrl` and `incidentsCsvUrl` in `api.ts`), so the browser saves the file as it streams in; `lib/csvRange.ts` holds the range rules.

**Decisions beyond the ticket.** Times are written as Excel takes a date and time, `YYYY-MM-DD HH:MM:SS`, with the zone named in the header (`Local time (America/Chicago)`, `UTC time`), not ISO `…T…Z`, which Excel leaves as text. °C is rounded to one decimal. A UTF-8 byte order mark starts each file so Excel reads a name outside ASCII correctly; a script should read it as `utf-8-sig`. Only text cells are guarded against formulas: numbers come from the database and stay bare, so a negative °C remains a number. "Capped at retention" refuses a longer range (422, naming the limit), as the Incidents log refuses a window over 8 days, rather than clamping it silently; the incidents file allows a day more, as the log's week has a day to spare, since a 90-day local range runs an hour over 90 days across a clock change. On History, "incidents for the same range" are that Device's (`device=`, the one filter added to the log's); the Incidents page's download is the district's for the window shown. The incidents file names its range by the local days the window touches, and both name the Campus by its shortcode. Offline and Sensor fault rows carry the last good Reading in the peak columns, as `/api/incidents` does; an ongoing incident leaves the end empty and counts its duration to the moment of the export. The browser applies the server's range rules and disables both links with the reason, so a click never opens a JSON error. Nothing limits concurrent exports beyond the existing read limit; a 90-day Readings file is about 13 MB over 52 queries, with about 1.5 s of CPU for the local times.
